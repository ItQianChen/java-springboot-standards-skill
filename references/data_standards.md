# 数据建模、数据流转与 MyBatis 数据访问规范

本规范沉淀自典型 Spring Boot + MyBatis 业务项目的真实结构，适用于设计实体、DTO/VO、分页查询、动态 SQL、状态字段、用户归属数据和订单类历史数据。处理数据库建模、实体字段设计、接口数据契约、Mapper XML 或数据一致性审查时，必须先读取本规范。

## 1. 字段类型与命名规范

| 数据类别 | Java 类型 | 数据库/JSON 命名 | Java 命名 | 关键约束 |
| --- | --- | --- | --- | --- |
| 主键、外键、关联 ID | `Long` | `*_id` | `*Id` | 不用字符串承载数值 ID；跨端传输长整型 ID 时评估精度损失 |
| 金额、费率、数量单价 | `BigDecimal` | `*_amount` / `price` | `amount` / `price` | 禁止 `Double`/`Float`；运算显式指定精度和舍入模式 |
| 业务时间点 | `LocalDateTime` | `*_time` | `*Time` | 不用 `Date`；序列化格式在全局配置统一声明 |
| 日期 | `LocalDate` | `*_date` | `*Date` | 日期没有时间语义时不得用日期时间类型 |
| 状态 | `Integer` 或枚举 | `status` / `*_status` | `status` / `*Status` | 取值必须由常量或枚举收敛，禁止魔法数字 |
| 布尔语义 | `Boolean` 或受控 `Integer` | `is_*` / `*_status` | `isDefault` 等 | 数据库位宽和接口契约必须二选一并保持一致 |
| 集合/嵌套展示数据 | `List<DTO/VO>` | 通常无物理列 | `*List` / `*s` | 只放在 DTO/VO，不作为数据库实体的持久化字段 |

补充规则：

1. 数据库列名使用 `snake_case`，Java 字段使用 `camelCase`，并开启映射（如 MyBatis 的 `map-underscore-to-camel-case`）。
2. 表名、列名、Java 字段、Mapper 列引用必须保持三方一致；修改任一方时同步审查其余两方。
3. 建表 SQL 属于版本化交付物。没有 SQL 的存量项目，审查实体和 Mapper 变更时必须反推并补齐模型约束，不允许只改 Java。
4. 金额字段汇总 SQL 返回 `BigDecimal` 或 `Decimal` 类型；不存在“必定有结果”的假设时，业务代码必须处理空值。
5. 每张表显式定义主键；业务可读编号（如订单号）与数据库主键分开建模，不得用一个字段承担两种身份。

## 2. 公共审计字段与自动填充

具有管理操作的表统一保留：

```text
create_time  -> createTime  (LocalDateTime)
update_time  -> updateTime  (LocalDateTime)
create_user  -> createUser  (Long)
update_user  -> updateUser  (Long)
```

强制规则：

1. `INSERT` 填充四字段；`UPDATE` 填充 `updateTime`、`updateUser`。
2. 填充逻辑集中在 AOP 切面或 ORM `MetaObjectHandler`，由 Mapper/Repository 写入路径统一触发；禁止在多个 Service 重复手写。
3. 自动填充必须从线程上下文或认证主体取得当前用户 ID；系统任务没有用户身份时使用明确的系统账号，不写请求参数传入的 `userId`。
4. 审计字段属于服务端数据，不得由客户端请求 DTO 直接控制。
5. 自动填充依赖固定 setter 约定时，公共常量和方法签名必须有编译期或测试保障；实体字段改名必须同步修改填充器。
6. 更新语句必须写入 `update_time`/`update_user`，避免动态更新遗漏审计字段。

## 3. Entity / DTO / VO 数据分层

```text
Controller        请求 DTO / 分页查询 DTO     响应 DTO 或 VO
      │                        ▲
      ▼                        │ 对象转换
Service          业务实体 / 领域对象 ────────► 出参模型
      │
      ▼
Mapper/XML       持久化 Entity
```

职责边界：

1. Entity 只描述持久化结构和表关系，不承担接口契约职责。
2. 请求入参使用专门 DTO；字段校验、 Swagger 文档、默认值和兼容策略都定义在 DTO 上。
3. 页面聚合结果使用 VO；跨表名称、嵌套明细、报表序列等展示数据优先放入 VO。
4. 分页查询 DTO 独立建模，不与新增/修改 DTO 复用。
5. Controller 的出入参禁止直接使用 Entity；Entity 也不得作为 Feign 契约暴露。
6. 出入参转换可以在 Service 或装配器中完成，但必须保持转换边界清晰，禁止把展示字段回写到 Entity 再持久化。
7. 快照字段（商品名、单价、地址、联系人、图片等）在订单/合同类历史数据中冗余保存；关联 ID 只表达来源，不得作为历史展示依据。

## 4. 分页查询规范

1. 分页 DTO 统一包含页码和页大小，并设置默认值；页大小必须设上限，超出时回退到上限或拒绝请求。
2. 页码和页大小只接受整数；禁止用字符串拼接生成 `LIMIT`。
3. 使用 PageHelper 时，`startPage(page, pageSize)` 必须紧邻目标查询，中间不得插入其他查询、RPC、缓存读取或异步操作，防止分页条件串到错误 SQL。
4. 分页返回使用泛型 `PageResult<T>`，至少包含 `total` 与当前页数据；禁止未泛型的 `records` 导致调用方强制转换。
5. 查询结果先完成投影转换，再组装 `PageResult`；`total` 必须来自同一条过滤条件的 count。
6. 用户侧分页必须叠加用户归属条件；管理端分页可以全局查询，但必须由鉴权边界保证。
7. 列表接口只查列表需要的列；关联详情在需要时另行查询或用一次 JOIN 聚合，避免循环 N+1 查询。
8. 一对多列表分页时，分页对象必须是父表记录；不得让子表 JOIN fan-out 直接参与 `LIMIT` 和 count。
9. JOIN 引起父记录重复时，必须显式定义去重键和 count 口径，并让分页结果与总数使用同一业务定义。

## 5. MyBatis 映射与动态 SQL

基础规则：

1. `insert`/`update` 显式列出列名，不使用无列名全量插入，防止表结构变化造成隐式覆盖。
2. 参数一律使用 `#{}` 绑定；`LIKE` 拼接采用 `concat('%', #{field}, '%')`，禁止 `${}` 承载用户输入。
3. 动态查询使用 `<where>` + `<if>`；动态更新使用 `<set>` + `<if>`，并保证空条件时失败或不执行。
4. 集合参数使用 `<foreach>`；空集合必须提前拦截，避免生成 `in ()`。
5. 批量插入用 `<foreach>` 生成多值 `VALUES`，并设置单批上限，超限分批写入。
6. 插入需要回填主键时声明 `useGeneratedKeys="true"` 和 `keyProperty`；后续子表写入必须使用回填后的父 ID。
7. 动态排序字段和方向必须白名单校验；`${}` 只允许出现在白名单解析后的静态片段中。
8. 多表 SQL 显式写 JOIN 条件，不用隐式逗号连接；筛选列在多表重名时必须带表别名。
9. `SELECT *` 只允许临时排查；交付 SQL 显式列名，避免列权限、宽表传输和 resultMap 漂移。
10. XML 中的 `<`、`>` 按 MyBatis 规则转义或使用 `<![CDATA[...]]>`。

联表查询与 N+1 治理：

1. MyBatis-Plus 的 `BaseMapper`/`LambdaQueryWrapper` 面向单表 CRUD 和简单条件查询；多表投影、聚合报表、复杂过滤排序使用自定义 SQL，动态或可复用查询优先放 XML。
2. 一对一或补充少量展示字段时，用单条 JOIN 查询直接投影到 DTO；返回 DTO/VO，不把联表结果伪装成宽表 Entity。
3. 一对多且需要分页时，先分页查询父表，再收集父 ID 用有界 `IN` 批量查询子表，最后按父 ID 装配，避免 JOIN 行 fan-out 破坏分页与 total。
4. 禁止在 `for`/`stream` 循环中逐条调用 Mapper、RPC、Redis 或远程接口拼接列表数据；列表装配必须批量获取并用 `Map`/分组结果组装，父集合为空时直接返回空结果。
5. `IN` 查询必须设置单批上限并分批执行，默认 500；项目或数据库已有明确约定时以项目约定优先。跨库/跨服务数据不得 SQL JOIN，改用批量接口装配并定义失败策略。
6. 列表接口避免 MyBatis `association`/`collection` 的 `select=` 嵌套查询；它会为每行记录触发一次额外 SQL，形成 N+1。
7. 详情接口可用 JOIN + Nested Results：为父子对象配置能唯一识别的 `<id>`，重复列用 `columnPrefix` 区分；SQL 按父记录有序返回时设置 `resultOrdered="true"` 降低映射内存。
8. JOIN、过滤、排序、分组列必须有匹配索引，关联字段类型和排序规则一致；JOIN/WHERE 关键列不得套函数或做隐式类型转换导致索引失效。
9. 先用 WHERE、子查询或 CTE 缩小驱动结果集，再关联和分组；只 SELECT 需要的列，禁止为了省代码查询无用宽列。
10. 大表或高并发联表 SQL 合入前用 `EXPLAIN` 检查访问类型、索引命中、预估扫描行数和 JOIN 顺序，并根据结果补索引或改写 SQL。

对象映射：

1. 查询返回类型明确到 DTO/Entity，不依赖未命名的 `Map`。
2. 表字段与 Java 字段通过 camelCase 映射或显式 `resultMap` 对齐，不使用拼音缩写和双重命名。
3. XML 的 namespace 与 Mapper 接口全限定名一致，SQL `id` 与接口方法一致。
4. 修改字段时同步检查实体、XML、DTO/VO、建表 SQL、接口文档和历史数据兼容。

## 6. 状态字段与状态流转

1. 同一业务状态只在一个常量类或枚举中定义；订单状态、支付状态、配送状态不得互相混用。
2. 状态值及其含义必须在模型注释、枚举或常量中完整声明，禁止只写在业务代码分支里。
3. 状态变更前必须先读取当前持久化状态，校验当前状态和目标状态是否满足迁移表。
4. 状态更新语句必须带当前状态条件或通过受保护领域方法执行，防止并发双写覆盖。
5. 状态变更伴随时间、原因、操作人等痕迹字段时，同一次写入或同一事务内更新。
6. 定时任务补偿状态时同样校验迁移合法性，并记录扫描范围、命中条件和处理结果。
7. 报表统计的状态集合必须显式列出，如“有效订单”必须定义包含哪些状态，不得用一个数值隐含全部业务口径。
8. 状态常量不得散落在实体、Service、前端契约三处重复定义；需要跨端一致时从契约生成或建立同步测试。

## 7. 用户归属与数据边界

1. 当前用户 ID 必须来自 JWT/Session 解析后的上下文，禁止信任请求体或 URL 中的 `userId`。
2. 用户侧创建数据时，服务端从上下文补齐归属 ID，再执行写入。
3. 用户侧查询、详情、修改、删除必须把归属 ID 放入 SQL 条件；仅靠前端不展示他人数据不构成权限边界。
4. 管理端接口通过独立路径、拦截器和角色校验隔离；用户端与管理端 Controller 不混用。
5. 订单、地址、购物车等用户数据至少校验归属；跨用户访问返回业务不存在或无权访问，不区分暴露资源是否存在。
6. 匿名可访问接口必须显式白名单；支付回调、公开状态查询等接口按来源和签名校验，不套用普通登录态规则。

## 8. 敏感数据与配置红线

1. 数据库、Redis、对象存储、地图、第三方登录和支付配置必须来自环境变量、部署平台密钥或受访问控制的配置中心，禁止提交明文配置文件。
2. 开发示例配置只允许占位符，且不得复用任何真实环境的账号、主机、桶名或密钥。
3. 日志不得输出完整 Token、密码、密钥、Authorization 头；请求日志默认脱敏。
4. 手机号、身份证、银行卡、详细地址等 PII 在响应和日志中脱敏；内部管理端确需明文时必须有权限与审计。
5. 密码不得使用裸 MD5/SHA。新增系统使用 Argon2、bcrypt、scrypt 或 PBKDF2，并加盐；存量 MD5 数据必须规划迁移和重置策略。
6. 上传文件地址、支付凭证、回调报文只保存必要字段；凭证类数据加密或托管保存。
7. 生产明文密钥已经泄漏时，修复顺序是先撤销/轮换密钥，再清理仓库历史和本地配置，最后补齐扫描规则。

## 9. 数据规范审查清单

- [ ] 字段类型是否满足第 1 节映射？金额、时间、状态、ID 是否使用正确类型？
- [ ] 实体、Mapper XML、建表 SQL、DTO/VO 和接口文档是否同步？
- [ ] 审计字段是否由统一切入点填充？更新语句是否写入审计字段？
- [ ] Controller/Feign 是否直接暴露 Entity？请求和分页是否使用专门 DTO？
- [ ] 分页参数是否有默认值和上限？`startPage` 是否紧邻目标查询？`PageResult` 是否泛型？
- [ ] SQL 是否全部参数绑定？动态排序是否白名单？批量集合是否处理空值？
- [ ] 状态是否由常量/枚举收敛？状态变更是否先读后改并校验迁移？
- [ ] 用户侧数据是否都带上下文归属条件？匿名接口是否显式白名单？
- [ ] 历史订单是否保存商品、地址、联系人和价格快照？
- [ ] 配置密钥、Token、PII、密码哈希是否满足第 8 节红线？
